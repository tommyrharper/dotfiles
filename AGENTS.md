# Project notes for agents

Deliberate decisions in this repo - do NOT silently revert them:

- `homebrew.onActivation.cleanup = "zap"` in `configuration.nix` is intentional. It forces the good habit of declaring every Homebrew package in the Nix config instead of installing things ad-hoc, which keeps the machine reproducible. Do not soften it to `uninstall` or `none`. Users are warned about its effect in README.md; this note is for anyone tempted to change the setting itself.
- Never commit `.no-mistakes/` validation evidence to this public repo. `.no-mistakes/` is gitignored; if a validation pipeline stages evidence into a branch, drop it before merging.
- Private-file pattern: for any per-machine secret (Hetzner host, SSH private hosts), keep a gitignored real file (`home/.config/zsh/private-env.zsh`, `home/.ssh/dotfiles.config.private`) alongside a committed `.example` template, and have the relevant `home.nix` module read/Include it by path so Nix never embeds the content in the store. Follow this same shape for the next private value instead of inventing a new mechanism.
- SSH config is fragment-managed, not whole-file-managed: `~/.ssh/config` itself is never a home-manager-generated file (Colima and other tools must be free to rewrite it). `home.nix` only symlinks `home/.ssh/dotfiles.config.public.{darwin,linux}` and `dotfiles.config.private` into `~/.ssh/`, then an activation script idempotently prepends `Include` lines for them. Do not reintroduce a `programs.ssh`-style whole-config approach.
- `home.nix` enables home-manager's native `services.ssh-agent` module on Linux only (`!isDarwin`), so a minimal Ubuntu server (no gnome-keyring/desktop) gets a persistent `systemd --user` ssh-agent that keeps a key unlocked across shells, with `SSH_AUTH_SOCK` auto-wired into `programs.zsh`. Do not hand-roll a shell-rc `eval $(ssh-agent)` mechanism instead - the native module already does this and is covered by `tests/ubuntu-support.test.sh`. Left disabled on macOS since launchd + Keychain (`UseKeychain`) already provide this for free there. Enabling the systemd unit alone is NOT enough on a headless server: without `loginctl enable-linger`, systemd-logind kills the user's whole `systemd --user` instance (agent included) the moment the last login session for that user closes, so every fresh SSH connection gets a brand-new empty agent and the passphrase prompt returns - verified end-to-end on a real Ubuntu VM with genuine independent SSH sessions, not `docker exec` (a plain container exec never exercises logind's session-count teardown, so it can't catch this). `home.activation.enableSshAgentLinger` in `home.nix` runs `loginctl enable-linger` on every rebuild to cover this; it needs no sudo and takes effect immediately, no reboot or re-login required. This activation entry is a no-op string on Darwin but still shifts the generated activation script text, so it moved `tests/ubuntu-support.test.sh`'s pinned `EXPECTED_DARWIN_DRVPATH` - re-pin that constant again alongside any future deliberate macOS-affecting change, per the comment above it.
- The Linux login shell must be the Nix zsh, and `bootstrap.sh`'s Linux step 5 (`sudo chsh`) is what makes it so. `home.nix` configures `programs.zsh` only, and home-manager's `services.ssh-agent` module injects `SSH_AUTH_SOCK` solely into the shells it manages - so on Ubuntu's default `/bin/bash` login shell the systemd agent runs but no shell can reach it, and every `git pull` re-prompts for the key passphrase no matter how correct the agent, linger, and `AddKeysToAgent` wiring is. Don't "fix" that class of bug by enabling `programs.bash` as well or hand-writing `SSH_AUTH_SOCK` into a bash rc; the login shell is the root cause. The step never `chsh`es to a zsh that fails to start - `sshd` gives you your login shell and nothing else, so a bad one is a total SSH lockout - and `tests/ubuntu-support.test.sh` runs that guard against stubbed `getent`/`chsh`/`sudo`. macOS already logs into zsh, so the step stays inside the Linux branch.
- `tools.nix` is the single source of truth for every managed CLI tool and GUI app; README.md's "Package metadata" section owns the field semantics and selection logic. `tool-selection.nix` holds the shared predicates parameterized by `currentPlatform`; don't hand-maintain separate brew/cask/Linux package lists. `configuration.nix` hardcodes macOS selection, while `home.nix` derives the platform per macOS/Ubuntu output, since a single file-level constant can't be right for both targets at once. `scope = "personal"` entries are gated by one shared `usePersonalSetup` module argument (required, no default - nix-darwin doesn't honor plain Nix argument defaults for custom module args, so both `specialArgs` and the Linux outputs' `extraSpecialArgs` in `flake.nix` must always supply it). Its value is never edited in `flake.nix`: that file builds every target once per profile (`mac`/`mac-basic`, `<user>@<system>`/`<user>@<system>-basic`), and the machine's choice lives in the gitignored root `.env`, which `setup-env.sh` turns into the `-basic` output suffix for `bootstrap.sh`/`rebuild.sh`. Don't "simplify" this into `flake.nix` reading `.env` directly - Nix evaluates this repo as a git tree, so untracked files never reach the store and `builtins.readFile ./.env` fails to find it; and don't make either script fall back to a default profile, since silently building the wrong one is worse than refusing to start. See README.md ("Setup profile") and `tests/setup-env.test.sh`. Any `home.nix` line shared between the macOS and Ubuntu branches must be explicitly gated per platform; `tests/ubuntu-support.test.sh` pins the macOS drvPath and fails if Linux-only work leaks into the macOS derivation. `lib.mkIf` is not always enough to gate: on a `lazyAttrsOf` option like `home.sessionVariables`, a `mkIf false` *leaf* leaves the attribute present-but-`null` in the other platform's evaluation instead of removing it, so gate the whole attrset with `lib.optionalAttrs` instead (both `DOCKER_HOST` and `NPM_CONFIG_PREFIX` hit exactly this) - and confirm the absence with `nix eval ... --apply builtins.attrNames`, not by eyeballing the gate.
- `agent-capabilities.toml` + `agent-capabilities.sh` are the source of truth for expected Codex/Claude Code/Pi/opencode skills, Claude Code plugins, and repo-authored Pi extras (see README.md, "Agent capabilities"). It deliberately delegates to each ecosystem's own install mechanism instead of hand-copying files: skills go through the real `skills` CLI (skills.sh, already declared in `tools.nix`), Claude plugins through `claude plugin marketplace add`/`install`. Never hand-roll a second package manager here or copy directly into `~/.agents/skills`/`~/.claude/skills`/plugin caches - shell out to the existing tool. opencode natively reads `~/.claude/skills` and `~/.agents/skills` as compatibility sources (verified against its docs), so it needs no separate sync step.
- No `home.nix` activation script (any of them, not just `installNativeTools`) may assume a bare command name resolves - Home Manager activation runs with a curated PATH, not the base image's or a login shell's - and `home.sessionVariables` is not in scope there either (the generated `activate` script never sources `hm-session-vars.sh`), so anything activation needs in its environment must be exported inline as well, even when a session variable already sets the same value. Two failure modes bit us: (1) a Nix-manageable tool (tar, gzip, coreutils) missing from `home.packages`/the script's PATH export - fix by adding it there; (2) a system-owned, non-Nix binary (`loginctl`, part of systemd) not found by bare name at all - fix by calling it via its known absolute path (e.g. `/usr/bin/loginctl`), never assume PATH lookup for these. Each activation block must also stay individually fault-isolated (`(...) || echo "WARNING: ..." >&2`) since these scripts run under `set -e`; see `tests/ubuntu-support.test.sh` for the executable regression coverage. Verify against a real minimal-base activation run, not just `nix eval` - a container/VM with an unusually complete PATH can mask both failure modes.
- `herdr integration install <target>` is intentionally imperative inside `home.nix` because herdr has no declarative integration config; README.md's "About `herdr`" owns the user-facing details. Keep `installHerdrAgentIntegrations` active on both platforms, with Linux ordered after `installNativeTools`, and re-pin `tests/ubuntu-support.test.sh`'s `EXPECTED_DARWIN_DRVPATH` alongside any deliberate macOS-affecting change.
- Rootless Docker on Linux is split deliberately: `home.nix` owns the `systemd --user` `docker` unit and `DOCKER_HOST`, but the setuid `newuidmap` it depends on comes from `bootstrap.sh`'s `sudo apt-get install -y uidmap` step. Home Manager cannot install a setuid binary, so do not try to move that package into `tools.nix`/`home.packages` - a Nix store `newuidmap` is on PATH but powerless, which is a harder failure to read than the missing-binary one. See README.md ("Rootless Docker").
